Reviewed range: full diff of 7853dde5 against its parent (base migrate.go@a81592b5)

Bug being fixed: previously, once the migration request context expired
(deadline/cancel), both the post-readback rollback path and the
readback-timeout-vs-missing-fence distinction used that same expired `ctx`.
That meant (a) rollback of an already-applied description write could itself
fail immediately because the context was already dead, and (b) a readback
that timed out was indistinguishable from a genuinely absent provenance
fence, so it was always resolved as a hard "missing fence" rollback rather
than an honest UNKNOWN.

Fix, verified by reading (not just diffing):
- `deriveMigrationPhases` (migrate_phase.go) splits one apply into
  planning/mutation/readback contexts (still children of the original op
  context, so bound by the same deadline/cancellation) and a `rollback`
  context built via `context.WithTimeout(context.WithoutCancel(op), budget)`
  — genuinely detached from the parent's cancellation, so a rollback attempt
  is never doomed by the request that already expired. `phases.cancel()` is
  deferred, so all four are released on return; no leak.
- `finishMigrationRollback` (migrate.go:861) is now the single rollback exit
  used at both call sites (post-write journal failure, and post-readback
  !okRB) and always runs under `phases.rollback`. On failure it marks the
  journal `rollback_pending`, best-effort persists it, and returns
  `RollbackPendingError` up through `applyMigration`/`ApplyMigrationForRef`
  instead of silently leaving `RolledBack=false` with no durable trace — this
  is the part that actually matters for an R2/R3 change: an operator can no
  longer lose an unreconciled rollback silently.
- `readbackUnknown` (provider.IsTimeout) now distinguishes a timed-out
  readback (`"readback UNKNOWN: ..."`, no missing-fence claim, no bogus
  fallback re-GetTask) from a readback that actually came back empty
  (migrate.go:787-818). Traced both branches by hand; `okRB` stays false
  either way so rollback still fires, but the recorded detail is now
  truthful about which case happened — matters for whoever reconciles a
  `rollback_pending` journal by hand.
- `migrationRecoveryContext` (migrate.go:892) only re-wraps with a fresh
  budget when the incoming ctx has actually errored (`ctx.Err() != nil`);
  otherwise it reuses the still-live ctx as-is. Confirmed this doesn't
  regress the existing ambiguous-SetDescription-write reconcile path
  (`reconcileMigrationDescriptionWrite` called with `phases.mutation`,
  migrate.go:750): mutation is a plain `WithCancel(op)` with no independent
  deadline of its own, so behavior there is unchanged from before this diff.
  The new independent-budget behavior only actually engages through
  `phases.rollback`, which is exactly the path the fix targets.
- `RefusePendingRollback`/`PendingRollbackJournals` (migrate_phase.go) are
  wired fail-closed pre-side-effect in both `ValidateLaunch` (gate.go:96,
  before the provenance/status checks, returns `BlockedError{Code:
  "rollback_pending"}`) and `runApprove` (cmd/herd/main.go:3036, before the
  canonical transaction lock is acquired) — both correctly precede any
  mutating step. `"rollback_pending"` was also added to `hardSelectionCodes`
  (gate.go:53) so it fails the whole `SelectEligibleRefs` run rather than
  being swallowed as "zero eligible", matching the existing hard-failure
  contract for `capability`/`stale`/`unresolved`.
- Traced the one production caller of `ApplyMigrationForRef`
  (cmd/herd/deps.go:366) and confirmed the exported signature is unchanged,
  and confirmed the two existing `ValidateLaunch` test files
  (validate_launch_scoped_test.go, deps_test.go) don't touch rollback
  journals, so the new gate check can't spuriously fire there — verified no
  stray `.herd/migrate-journal` (or `HERD_MIGRATE_JOURNAL`-pointed) directory
  exists in this tree that would make the new gate check fire against
  unrelated pre-existing state.
- `Journal.Status` is `omitempty`, and legacy journals without it are read
  via `PendingRollbackJournals` — an absent/empty status is simply not
  `rollback_pending`, so old journal files don't spuriously trip the new
  gate. No migration of on-disk journal shape required.

No blocking finding. Residual risk: `RefusePendingRollback` does a journal
directory read on every `ValidateLaunch` and every `herd approve` invocation
— an added stat/read on a hot pre-side-effect path. Given it's a single
small-directory scan gated by a status field and this class of correctness
bug (silent unreconciled rollback) is exactly what R2/R3 gating exists to
prevent, I don't consider this a blocking concern, but flagging it as
residual for the supervisor's awareness rather than silently accepting it.
