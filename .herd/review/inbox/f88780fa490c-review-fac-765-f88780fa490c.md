### 2. `reviewingest.go` harvest-branch-scope change — test does not prove the change (BLOCKING)

The diff adds a `latestExact` tie-break in
`resolveHarvestCandidateWithReconstructionAt`: alongside the existing
`latest` (latest-by-timestamp among ledger rows whose SHA is
`reachableFromBranch(repoRoot, row.SHA, branch)`), it now separately tracks
the latest row whose *recorded* `row.Branch` string exactly equals the
requested `branch`, and prefers that when non-empty.

The only new test for this, `TestHostLabelledHarvestSelectsExactBranchBoundPass`
in `cmd/herd/harvest_branch_scope_test.go`, builds two sibling branches
(`herd/fac-652`, `herd/fac-670`) both branched directly off the same `main`
commit with no merge between them, records a host-labelled PASS for each,
and asserts that resolving `herd/fac-652` returns the fac-652 SHA and not
fac-670's.

That assertion already held before this diff, independent of the new
`latestExact` logic: `reachableFromBranch` (pkg: `commitIsAncestor` →
`git merge-base --is-ancestor`) excludes `fac670SHA` from consideration
entirely when resolving `herd/fac-652`, because fac670's commit is not an
ancestor of `herd/fac-652`'s tip — it goes into the pre-existing `offBranch`
bucket and is `continue`d past before either `latest` or `latestExact` is
ever touched. `fac652SHA` is the only row that survives that ancestry filter,
so it is trivially selected as both `latest` and `latestExact`, and the test
passes with the `latestExact` branch entirely deleted.

The real case `latestExact` is meant to guard — two ledger rows for the
*same* target branch resolution, both reachable from that branch's tip (e.g.
one via a shared ancestor after a rebase/merge), but recorded under
different `Branch` label strings, where the timestamp-only `latest` would
pick the wrong one — is not constructed anywhere in this diff. As written,
this new production code path has zero non-vacuous test coverage: reverting
just the `latestExact` addition would not fail any test in the diff.

I could not execute `go test` to confirm this mechanically (no Go toolchain
on this host — see Tests run below), and per the pool-review contract I did
not swap or revert any tracked file in place to demonstrate it; the vacuity
follows directly from reading `reachableFromBranch`'s ancestry semantics and
the test fixture's branch topology, which is fully determined by the diff
and fixture code as written.

Correction: either (a) construct a fixture where the off-branch row's SHA
*is* reachable from the target branch (e.g. record it against a shared
ancestor commit, or a commit that gets merged into both branches) so the
ancestry filter alone cannot explain the selection, or (b) unit-test the
`latestExact` comparison directly against two same-reachability rows with
differing `Branch` fields and differing timestamps.
