## Static review (no blocking findings identified)

Both commits reviewed together, since `0f177d48` is a direct, narrow follow-up
fix to a bug in `5fa955d1` and cannot be judged in isolation:

- `5fa955d1` introduces `safePublicationBranch(branch, defaultBranch)` gating
  lane-push branch-publication authority. Its guard was
  `defaultBranch != "" && branch == defaultBranch` — when `defaultBranch` is
  empty (unknown), that comparison is always false, so an unknown protected
  branch does **not** block publication. A lane could be granted push
  authority to `master` or `trunk` when the repository's actual default
  branch is unknown to the caller, because only the literal string `"main"`
  was hard-refused. This matches the described prior independent FAIL for
  `5fa955d1`.
- `0f177d48` closes exactly that gap by adding `defaultBranch == ""` as an
  unconditional refusal in `safePublicationBranch`, with a comment explaining
  why an unknown default cannot be assumed to be `main` (real repos may use
  `master`, `trunk`, `develop`, etc.). This is a minimal, correctly-scoped
  fix — it does not touch any other branch of the gating logic.
- `standingEnvelope` (added in `5fa955d1`) resolves the lane's native
  worktree branch via `opts.WorktreeHead` only when the policy actually
  requests lane-push, and fails closed (returns an error, no envelope) if
  `WorktreeHead` is nil or errors, or if `safePublicationBranch` rejects the
  resolved branch — `runRaise` propagates that as `OutcomeFailed` rather than
  silently downgrading to no-push.
- `AllowedBranch` is only ever populated via `branchIf(canPublish, branch)`,
  and `canPublish` requires: policy is `lane-push`, lane authority is
  `write`, lane has `git-write` capability, lane role is not `reviewer`
  (case-insensitive), and `safePublicationBranch` passes. All five
  conditions are conjunctive (`&&`), so removing/weakening any one of them
  fails closed to no-push (`forbidden` gets `"push"` prepended).
  `ForbiddenActions` still always carries `"open or update a PR"`, `"merge"`,
  `"self-review"`, `"change standing policy or authority"` regardless of
  `canPublish`, so a lane-push grant never implies PR/merge/self-review
  authority.
- Rendered vs. durable consistency: `withContinuationGoalAndEnvelope` now
  takes the same resolved `envelope` that is persisted via
  `SetGoalWithAuthority`, replacing the prior call to
  `AuthorityEnvelopeForLane(lane)` inside `withContinuationGoal` (which would
  have silently re-derived a *policy-free* envelope, independent of whatever
  was just persisted — a rendered/durable divergence bug that predates this
  range and is fixed here as a side effect of threading `envelope` through).
  Test `TestLanePushStandingGrantMatchesRenderedAndDurableAuthority` asserts
  the rendered prompt text and the durable `AllowedBranch`/`ForbiddenActions`
  agree.
- New tests in `0f177d48` (`TestLanePushStandingGrantFailsClosedForNonWritersAndProtectedBranches`
  extension) directly cover the fixed defect: unknown default branch (`""`)
  refuses publication for `master`, `trunk`, and an arbitrary feature branch
  alike; a known default of `main` still allows an assigned feature branch;
  a known default of `master` still refuses publishing `master` itself. This
  is exactly the "new unknown-default refusal and known-default positive
  cases" the task calls for, and the assertions are on `AllowedBranch`/
  `ForbiddenActions` state, not solely a nil-error check, so they are not
  vacuous against the pre-fix code (pre-fix, the `master`/`trunk` unknown-
  default cases in `TestLanePushStandingGrantFailsClosedForNonWritersAndProtectedBranches`
  would fail: `AllowedBranch` would be non-empty).
- `AllowedBranch` uses `json:"allowed_branch,omitempty"` — an empty grant
  omits the field entirely rather than serializing a misleading empty string
  for the no-push case.
- Path/branch value validation (`strings.HasPrefix(branch, "-")`,
  `..`, `//`, leading/trailing `/`, empty path segments) is unchanged by this
  range and was not the subject of the described prior FAIL; not re-litigated
  here.

No caller-supplied flag or config path was found that can force `canPublish`
true independent of the five conjunctive conditions above, and no path
defaults an unknown protected branch to `main` — the opposite is now
enforced.
