## Root-caused, not just observed

`matchCombinedRangeReplay` (reconcile.go) shells out to
`git merge-tree --write-tree --merge-base <base> <windowBase> <candidate>`.
This repo's only available git anywhere on this host is 2.34.1:

```
$ git --version
git version 2.34.1
$ git merge-tree --write-tree --merge-base <b> <b> <c>
usage: git merge-tree <base-tree> <branch1> <branch2>
```

The three-way, tree-writing `git merge-tree` invoked here was added in git
2.38 (Oct 2022); 2.34.1 only understands the legacy two-arg conflict-marker
form. The mismatched flags produce a non-zero exit, `gitOut` returns an
error, and `matchCombinedRangeReplay`'s loop does `if mergeErr != nil {
continue }` — so every candidate window is silently skipped and the fallback
reports "no matching window" regardless of whether the replay would actually
have succeeded.

This is not a version requirement introduced by this candidate:
`pkg/review/pipeline.go:538` and `:562` already call `git merge-tree
--write-tree --merge-base=...` in existing, pre-candidate production code
(the review pipeline's own merge-tree probe). This repo's production/CI
target already assumes git >= 2.38; this sandbox's system git (2.34.1, the
only git anywhere on `$PATH` or common install locations on this host) does
not meet that baseline. I confirmed no newer git is available here via
mise, asdf, or any other path on the host.

Manually tracing `matchCombinedRangeReplay` against the test fixture (base →
main-side context edit → landedFirst → landed, stackLen=2, tip patch match at
`landedCommits[end=2]`, `windowBase = landedCommits[0]` = "main advances")
the replay it constructs — three-way merge of `windowBase` and `candidate`
using `base` as merge-base — is exactly the rebase-replay the fallback is
supposed to prove, and should produce a tree identical to `landed` once run
under a `git merge-tree` that supports `--write-tree --merge-base`. I cannot
independently execute that path here to confirm it, only reason about it.
