# Herdforge Architecture and Fleet Audit — 2026-08-02

## Executive verdict

Herdforge is pointed at the right problem and already has a useful CLI, provider abstractions, deterministic task ordering, worktree utilities, review primitives, and active self-hosting. It is not yet safe or complete enough to replace the Chainseer shell fleet as an unattended, repo-agnostic work factory.

The main constraint is not the number of builder agents. It is the absence of one durable, fail-closed lifecycle connecting claim, cwd-bound dispatch, completion, verification, independent review, serialized integration, board reconciliation, and cleanup. Several packages implement pieces of that lifecycle, but the running paths do not compose them transactionally. Adding more builders before that control loop exists increases root-checkout collisions, stranded cards, review pressure, and recovery work.

The recommended architecture is defined in [TARGET-WORKFLOW.md](TARGET-WORKFLOW.md).

## Audit scope and snapshot caveat

This was a read-only audit of:

- the code graph and selected source paths;
- all Kaneo tasks, with detailed inspection of every To Do card;
- active and recently completed Herdr agent panes;
- the current GitHub pull-request and CI history;
- the 75 `herd-*` scripts in the Chainseer `bin/` directory;
- repository configuration, lane registry, prompts, tests, and package wiring.

The fleet continued merging changes during the audit. Counts and transient failures below are therefore observations, not a frozen release assessment. The final board snapshot contained 118 tasks: 80 done, 29 To Do, 8 in progress, no tasks in review, and 1 archived. The final GitHub snapshot was `4857546`; CI and `make ci` were green at that point.

## What is working

- The project builds and its hermetic `make ci` gate passes all current package tests, `go vet`, and preflight.
- GitHub CI was green on the latest `main` snapshot and recent merged pull requests.
- Harness health was good for Claude, Codex, Grok, Kimi, Antigravity, and OpenCode discovery; the doctor reported valid shared configuration.
- Kaneo selection implements the required deterministic `(priority DESC, ticket ref ASC)` ordering.
- The provider interface, Herdr adapter, worktree manager, dispatch packet, review ledger, shared-checkout lock, and reconciliation utilities are useful foundations.
- The fleet has demonstrated real self-hosting throughput and recovered several overlapping/contaminated changes without losing the repository.
- Preflight currently reports zero absolute-path leaks.

These are meaningful foundations. They do not yet prove the end-to-end invariants because many packages are tested in isolation and several production paths bypass them.

## Highest-risk gaps

### 1. The daemon does not run the factory lifecycle

`pkg/daemon.Engine` holds provider, router, store, worktree, and verifier dependencies, but its pulse path only lists, selects, claims, and records a task. It does not create an isolated task worktree, launch a cwd-bound agent, verify completion, dispatch review, integrate, reconcile, or clean up. The long-running daemon is a fixed sleep loop around that partial claim operation.

The one-shot `herd forge` path is more dangerous: after claiming work it can choose an arbitrary in-progress task and advance it toward review without proof that the worker finished, committed, or passed verification. It does not establish an independent reviewer verdict before the later approval path checks merge evidence.

### 2. Claim and dispatch are not atomic or recoverable

The Kaneo claim is a status update to `in-progress`; the role is not atomically bound, and no compare-and-set, fencing token, or lease prevents two processes from claiming the same card. Board mutation occurs before several local operations. A store, worktree, launch, or delivery failure can therefore leave a card stranded.

The local claim store does not provide a unique active-claim constraint or a completed/released lifecycle. The current in-memory claim manager only coordinates one process. There is no durable outbox tying board writes, event persistence, session launch, and prompt delivery together.

### 3. Worktree isolation is promised more strongly than it is enforced

The live fleet exposed this directly: one worker committed from the shared root while behind upstream, and the coordinator had to recover a contaminated checkout. Current launch data does not consistently carry an explicit cwd into Herdr. Some commands create persistent lane worktrees, some create task worktrees, and some launch in the root/default directory while relying on the prompt to tell the agent to change directories.

Dispatch also records a task branch name that can differ from the branch Git actually created. Worktrees are based on the current local `HEAD`, not a fetched immutable `origin/main`. Anchor-ref creation is best effort, and cleanup/recovery behavior is not uniformly fail-closed around unique work.

### 4. Completion, verification, and review are not revision-bound end to end

Workers can be considered complete based on pane or board state rather than a committed candidate SHA and evidence receipt. The generic verifier accepts an empty command, splits configured commands with `strings.Fields`, and its mutation-check function currently reruns the same suite without actually introducing the supplied mutant. That cannot prove test non-vacuity.

Review dispatch is branch/card oriented rather than an immutable SHA contract. The risk classifier never returns R2, and model execution backend is conflated with author/reviewer family in parts of the routing model. Fallback can lose the different-family guarantee instead of failing closed. The review rebase helper uses an invalid `git merge --rebase` form and operates against the shared repository.

### 5. Harvest is observation, not integration

`herd harvest` scans worktrees but does not perform the reviewed merge pipeline implied by its name. Some Git fetch/cherry failures are converted to clean/no-work results, output order is concurrent and nondeterministic, and Herdr attention collection contains an explicit stub. The CLI can print scan errors without propagating a non-zero exit.

Board completion is safer than earlier transitions because it looks for `origin/main` evidence, but that makes review/approval post-merge evidence rather than a pre-merge gate. A single integration owner and exact-SHA ledger are still missing from the live path.

### 6. Several fail-closed invariants are violated in package code

Examples found during the source audit:

- direct Kaneo HTTP handling does not consistently reject a `200 OK` body containing an error object;
- webhook HMAC verification accepts missing secret or signature values;
- webhook handler errors can still result in success responses;
- Redis mail subscribes with a literal wildcard and ignores publish errors;
- malformed mailbox JSON is silently skipped and file locking is process-local;
- cron jobs ignore the actual cron expression and run under a locked minute loop while swallowing handler errors;
- garbage-collection Git errors can be interpreted as zero commits ahead;
- salvage patches are placed under an ignored state path before a worktree may be removed.

These are incompatible with unattended destructive or state-mutating operation until corrected and tested.

## Package integration assessment

The knowledge graph indexed 164 Go files, 1,567 nodes, 15,663 edges, and 48 communities during the audit. Its community and flow output was unusually fragmented—most flows stayed within one file and it reported no cross-community edges—so graph dead-code and architecture conclusions were confirmed against source rather than accepted at face value.

Two files dominate orchestration complexity: `cmd/herd/main.go` is roughly 3,000 lines and `pkg/lifecycle/lifecycle.go` roughly 1,900 lines. The latter has no tests. The graph also found more than 180 apparently unreferenced symbols, mostly types or interface-driven false positives, but it highlighted genuine stubs and shell-port residue.

At the snapshot inspected, these packages had no production consumer outside their own package/tests: budget, claim, conflict, cron, graph, llm, mail, memory, metrics, notifier, plugin, release, security, server, skill, tui, webhook, and worker. Several are proof-of-concept implementations rather than the capability their package name suggests:

- graph is an in-memory graph, not repository discovery or code-review-graph integration;
- plugin/skill validate or prefix bytes rather than execute WASM;
- worker supervises an in-memory map, not worker processes;
- server exposes a small health/OpenAPI surface, not the control plane;
- security uses simple substring checks;
- metrics and budget are in-memory and not wired into dispatch decisions;
- local LLM support is a narrow Ollama generate call rather than a complete Ollama/vLLM adapter.

Package count is therefore a misleading readiness metric. The next work should integrate or deliberately defer packages around one tested lifecycle instead of expanding the ownership grid.

### To Do quality

The remaining To Do queue was not dispatch-ready as a whole:

- 20 of 29 cards had an empty description;
- every To Do card had zero labels, so role matching cannot distinguish smith, worker, reviewer, or control-plane work;
- most cards had no explicit dependency relationships;
- the Herdforge project itself had no description defining the execution contract;
- several titles still carry mismatched legacy references such as a card ref and a different FAC number in the title;
- FAC-72 remained To Do despite a prior implementation attempt and repeated dispatch comments;
- FAC-118 is an explicit salvage/integration task, evidence that branch/worktree state and board state are not reconciled automatically.

The queue contains important missing control-plane work—drain, feedback, fresh-build, harvest-merge, pulse, quota supervision, review classify/ingest/mechanical/supervisor, settle-driven watch, wind-down, board freeze, and verification tooling—but empty cards should be groomed before more workers harvest them.

### Priority and dependency concerns

The urgent/high control-loop work was claimed while the audit ran, but the remaining foundational ports mostly have `no-priority`. The board does not express a critical path from atomic claims and callbacks through verification, review ingest, integration, and cleanup. Without that graph, deterministic sorting is stable but not necessarily useful: it can reliably select a task that is not actually the best unblocker.

## Chainseer parity assessment

Chainseer contains 75 `herd-*` scripts. Herdforge exposes many recognizable operations, including activate, attention, board-done, board-sync, cleanup, dispatch, kick, lifecycle, lock, lost, next, overlap, process, pulse, quota, resolve-lane, resources, review, review-ledger, route, selftest, send, standing, throughput, unmerged, and up.

Important behavior remains open or partial: drain, feedback, fresh-build, harvest-merge, hold, park lifecycle reconciliation, quota supervision, rescue, review classification/ingest/mechanical/supervision, settle-driven watch, stop/wind-down, tests-for, tool probing, and a verified continuous pulse. Some board cards marked done represent package primitives without a corresponding CLI or end-to-end behavior.

Do not port all 75 scripts literally. Chainseer mixes three layers:

1. portable Herdr mechanics such as terminal lifecycle, delivery, quota, and surface routing;
2. repository policy such as worktrees, board claims, verification, review, and merge gates;
3. Chainseer-specific conventions, state paths, refs, and command output contracts.

Herdforge should own layer 2, call Herdr for layer 1, and make layer 3 an adapter or project configuration only where it is genuinely reusable.

## Fleet assessment

The available model harnesses are sufficient. The missing fleet capacity is role separation and enforcement:

- the same OpenCode/DeepSeek family was configured for smith, worker, and reviewer, contradicting cross-family review;
- the lane registry warns that the observed Lazer/DeepSeek execution surface is last-resort or not proven write-capable, while live lanes used it for write work;
- the existing smith prompt named Chainseer and instructed direct pushing to `origin/main`;
- the harvest prompt also named Chainseer and lacked exact-SHA/evidence gates;
- there was no dedicated scout-planner, deterministic verification gate, review supervisor, or recovery sentinel contract.

No active agent needed a blind “are you done?” ping during the audit. The coordinator and reviewer were already reacting to callbacks and root-contamination evidence. The idle panes were mostly completed task tabs that should be reaped by lifecycle policy. State-specific recovery and cleanup are more useful than periodic generic nudges.

Spawn-ready contracts for the missing roles now live beside the existing prompts:

- `.herd/prompts/scout-planner.md`
- `.herd/prompts/verification-gate.md`
- `.herd/prompts/review-supervisor.md`
- `.herd/prompts/recovery-sentinel.md`

They are intentionally not wired to fixed models in this documentation-only change. Runtime registration should select healthy surfaces by capability and preserve model-family independence.

## Documentation and configuration contradictions found

- The README described a complete three-lane autonomous loop, although the daemon only claims and the one-shot forge path does not enforce completion evidence.
- Documentation used `review` while the board/provider convention is `in-review`.
- Documentation promised an ephemeral task worktree for every assignment, while several launch paths use persistent lanes or omit cwd.
- Prompts and examples hardcoded one cheap model for author and reviewer despite the different-family rule.
- Existing prompts carried Chainseer-specific commands and identities into a repo-agnostic project.
- The configured preflight command and documented `make preflight`/`make lint all` workflow were inconsistent.

The README, technical guide, skill guide, and prompt contracts were updated as part of this audit. Configuration and source were deliberately left unchanged.

## Recommended implementation order

1. Make the state machine and evidence schema explicit, durable, and crash-recoverable.
2. Add atomic cross-process claims, leases, idempotency keys, and a transactional outbox.
3. Enforce cwd-bound task worktrees from immutable `origin/main`; protect root and candidate refs technically.
4. Require a committed candidate SHA and deterministic verification receipt before review.
5. Bind different-family review verdicts to exact SHA/patch ID and fail closed on unknown family or stale evidence.
6. Add one serialized integration owner with post-merge gates, origin proof, board readback, and exact cleanup.
7. Add callbacks plus settle-driven reconciliation and capacity backfill.
8. Groom the board: descriptions, acceptance criteria, role labels, dependencies, and priority on every dispatchable card.
9. Integrate or defer isolated packages; split the command and lifecycle monoliths behind tested services.
10. Run crash-point, double-claim, stale-review, root-bleed, and unique-work-reap acceptance tests before unattended multi-repository rollout.

Until those gates exist, operate Herdforge as an assisted coordinator with human-visible integration decisions, not as an autonomous merge authority.
