# Herdforge Technical Manual & Agent Implementation Handbook

- **Version**: 1.0.0
- **Target Repository**: [`github.com/Kampe/Herdforge`](https://github.com/Kampe/Herdforge)
- **Primary Runtime**: Compiled Go binary (`cmd/herd`)

## 1. System Philosophy & Architecture Principles

Herdforge is designed as a **fail-closed, repo-agnostic software factory engine**. It allows human developers or standing AI agent fleets to run autonomous development lifecycles over any Git repository.

### Core Architectural Axioms
1. **Decoupled Task Infrastructure**: The daemon engine (`pkg/daemon`) knows *nothing* about specific task backends. It interacts strictly with `provider.TaskProvider` interfaces (`Kaneo`, `GitHub`, `Linear`, `Memory`).
2. **Strict Worktree Isolation**: Agents *never* operate in the main checkout root. Each assigned task spins up an ephemeral Git worktree (`pkg/worktree`) to prevent uncommitted file collisions.
3. **Multi-Model Provider Failover**: To prevent rate-limit (429) deadlocks, `pkg/router` dynamically balances requests across OpenAI, Anthropic, Google, and Ollama providers with automated cooldown timers.
4. **Adversarial Sized-to-Risk Reviews**: Code generated by a model family (e.g. Anthropic) must be reviewed by a *different* model family (e.g. Gemini/OpenAI) before git rebase-merging into default branches.

## 3. Go API & Interface Contracts

### 3.1 Task Provider Contract (`pkg/provider/provider.go`)

Any issue tracker or kanban board added to Herdforge must implement this Go interface:

```go
type TaskProvider interface {
    // GetTask fetches a single task by ID or issue number
    GetTask(ctx context.Context, id string) (*Task, error)

    // ListTasks lists candidate tasks filtered by project ID and status ("to-do", "in-progress", "done")
    ListTasks(ctx context.Context, projectID string, status string) ([]*Task, error)

    // ClaimTask transitions task status to "in-progress" and binds worker role
    ClaimTask(ctx context.Context, taskID string, role string) error

    // UpdateStatus updates the task status string
    UpdateStatus(ctx context.Context, taskID string, status string) error

    // AddComment posts an execution log or review comment to the task
    AddComment(ctx context.Context, taskID string, body string) error
}
```

### 3.2 Deterministic Task Sorting (`pkg/daemon/engine.go`)

To prevent agent thrashing, task selection is strictly deterministic across all providers:

$$\text{Sort Order} = (\text{Priority DESC}, \text{Ticket Ref ASC})$$

```go
priorityRank := map[provider.Priority]int{
    provider.PriorityUrgent: 4,
    provider.PriorityHigh:   3,
    provider.PriorityMedium: 2,
    provider.PriorityLow:    1,
}
```

## 4. Guide for Successive AI Agents

When taking up a ticket in `Herdforge`, follow this step-by-step TDD protocol:

1. **Preflight Verification**:
   ```bash
   go run ./cmd/herd preflight
   go test ./...
   ```
2. **Worktree Isolation**:
   - Create your working branch off `main`: `git checkout -b feat/your-feature`.
   - Ensure zero absolute paths (`/Users/...`, `/tmp/...`) are introduced into Go code, config files, or markdown docs.
3. **Write Tests First**:
   - Every new package or method must carry a corresponding `*_test.go` file with table-driven or mock-backed assertions.
4. **Verification Checkpoint**:
   - Run `go test ./...` and ensure exit code `0`.
5. **Commit Discipline**:
   - Follow Conventional Commits: `feat(scope): ...`, `fix(scope): ...`, `docs(scope): ...`.
